# Spec / Plan 方向评审

这是一场发散性的方向讨论，不是格式校对或验收清单。评审者带着自己的看法和思路进场，回答三个问题：
问题定义对不对；方案是不是业界对这个问题的成熟解法；它会不会给性能、可用性和扩展性留下长期的坑。

评审焦点放在方向与思路上；任务拆分、PR 大小、篇幅和章节格式留给 write-spec / plan 的后续迭代。
判断标准是路线正确、有利于架构长期发展和代码结构清晰；工作量大不是否定正确路线的理由。

本 skill 只读：不修改被评审文档、代码或 workflow 状态，也不构成设计接受或计划批准。用户采纳的意见经
`$dev-workflow-write-spec` 或 `$dev-workflow-plan` 整合进对应章节；推翻已接受方向的意见回到
`$dev-workflow-discuss-design`。

## 准备

1. 完整读取 `../workbench/references/workflow-contract.md`，尤其第 2.1 节（失败分类）和第 2.2 节（方向判断）。
2. 读取 `AGENTS.md`；按 contract 从当前请求 / memory 解析 `DOC_ROOT`，无可用记录时回退到仓库 `docs/workbench/`。
   读取 `DOC_ROOT` 下适用的 `AGENTS.md`。
3. 完整读取被评审文档。评审 plan 时同时读它消费的 spec；评审 umbrella 子任务时读 umbrella 中相关的路线与契约。
4. 后续轮次：用文档的版本历史（如文档仓库的 git diff）确认本轮改了什么、前几轮意见被如何吸收。用户已带理由否决的
   意见，没有新证据时不再重提。
5. 抽查文档中影响方向的代码事实，记录当前 `file:line`；文档里的代码描述可能已经漂移。
6. 建立业界对照：确定这个问题在哪些成熟系统或规范里出现过。相关源码在本地可用时（按 memory 或适用 `AGENTS.md`
   定位）优先读源码并记录 commit 或版本；否则查权威文档、上游 issue / PR。找不到对照时如实说明，不把印象当证据。

业界对照与代码核查可以并行交给 sub-agent。给 sub-agent 的是问题和待查系统，而不是自己的初步结论，避免它顺着
结论找证据；主 agent 复核其来源后再采用。

## 评审视角

按以下问题逐个思考；与当前文档无关的视角跳过，不为凑满而写。

1. **问题定义。** 文档要解决的真正问题是什么？它是在治症状，还是在治成因？换一个更上游的抽象或所有者，问题
   能否直接消失？
2. **业界解法。** 成熟系统怎样解决同类问题？文档方案与之相同还是不同？不同之处是绿地带来的领先、重新发明，
   还是走了对方已经放弃的路？借鉴的部分有没有连同对方的历史包袱一起照搬？
3. **最终形态。** 方案的最终形态是否清晰？有没有只为过渡或止血而存在、之后必须推翻的结构？方案是否被现有类型、
   ADR 或调用面牵着走（contract 第 2.2 节第 2 条）？
4. **所有权与边界。** 职责是否落在真正拥有它的组件？有没有跨层 guard / flag、平行路径、兼容 shim 或为假设性
   规范违反设计的补偿路径（contract 第 2.1 节）？
5. **长期的坑。** 性能：热路径上的额外拷贝、锁、序列化或逐行分派。可用性：生产拓扑下的单点、扇出放大、故障与
   恢复行为。扩展性：新增 connector、类型、算子或节点时的改动成本，规模放大后复杂度如何增长。
6. **硬上限与配额。** 列出文档新增的每个硬上限、配额和拒绝阈值，按 contract 第 2.2 节第 5 条检验：保护什么、
   依据是什么、为什么必须拒绝。依据不足的，建议删去或交给已有资源管理、背压和配置。
7. **外部依赖。** 方案是否需要 vendor 补丁、fork 或替换上游？按 contract 第 2.2 节第 4 条给出扩展点、升级或
   暂不支持并写明恢复条件的替代路线。

评审 plan 时另看：关键结构与流程是否忠实落实了 spec 的方向，有没有引入 spec 之外的新方向、长期不该存在的过渡
结构，或绕开 spec 裁决的所有者。Plan 暴露出 spec 本身的方向问题时，直接指出并说明需要回到哪个阶段。

## 怎样形成判断

- 每个关键问题都给出自己认为正确的方向，而不只是提出疑问。可以提出文档没有考虑的替代思路，包括重新定义问题。
- 区分证据强度：**事实**（代码、源码或规范可核查）、**推断**（由事实推出）、**待验证**（需要实验或进一步调研）。
- 与业界一致或已有明确共识的点，带证据直接给结论；只把真正的方向性分歧（存在多个合理方向、取决于产品取舍）
  交给用户，并附自己的推荐。
- 文档中方向正确的部分简短确认即可，篇幅留给需要改变的地方。

## 输出结构

在对话中输出，语言遵循当前请求和适用 `AGENTS.md`。按以下顺序组织：

1. **总体判断**：一段话说明方向是否正确，以及最关键的一到两个问题。
2. **问题与业界对照**：问题的本质；成熟系统的做法（系统、版本或 commit、具体位置）；文档方案相对它的位置。
3. **主要意见**：按对长期架构的影响排序。每条写清：现状（文档章节，必要时附代码 `file:line`）→ 为什么会成为
   长期问题 → 建议的方向 → 证据强度。
4. **上限与依赖审视**：文档涉及硬上限、配额或第三方依赖时，用表格列出“对象 / 保护什么 / 依据 / 建议”，建议取
   保留、改交资源管理或背压、删除、升级上游、暂不支持并写明恢复条件之一。不涉及时省略本节。
5. **其他思路**：发散的替代方案，或值得进一步讨论的方向。
6. **待用户裁决**：只列真正的方向性分歧，每项附推荐。没有时省略本节。

结尾请用户指出采纳、否决或想继续深挖的意见，按 workflow 进入下一轮修订或评审。

## 常见偏差

| 偏差 | 纠正 |
|---|---|
| 逐章挑措辞、格式或任务拆分 | 回到问题定义、业界解法和长期形态 |
| “改动面太大，建议先做最小改动或加开关” | 给出正确的长期路线；工作量不是取舍理由 |
| “与 ADR-xxxx / 现有类型一致，因此合理” | 它们只证明当前做法；判断做法本身是否正确 |
| “建议增加上限以防止……”，但没有依据 | 先回答保护什么、依据什么、为何必须拒绝；否则交给已有资源管理 |
| “可以给上游打个补丁” | 上游扩展点、升级版本，或暂不支持并写明恢复条件 |
| 只列问题，不给方向 | 每条意见都给出自己认为正确的方向 |
| 把业界共识点做成用户选择题 | 带证据直接给结论 |
| 照搬某个系统的实现细节 | 辨别那是成熟经验还是对方的历史包袱 |
| 第二轮重复第一轮已被否决的意见 | 先看版本差异；没有新证据不重提 |

## 问题

<未来架构师会问的那个问题，一句话。这是检索入口——写成问题，不是写成任务名。

检验：它应该是**任何人第一次接触这块代码时就会问**的问题。
出现具体故障、具体修复、PR 号或某个函数的缺陷，就是跑偏了，哪怕它语法上是个问句。>

## 背景与执行事实

<这一节是**模型说明书**，不是调查记录：只写「下一个改这块代码的人必须先知道」的事实。

优先用表格承载对照关系：有哪些实体、各自扛什么、谁按什么键、哪个 API 认哪种输入、
名字与实际是否一致、失败模式是什么形状（为什么静默、为什么只在某种形态下显形）。

带符号名锚点；不写会腐烂的行号。

能量化这类错误为什么会反复发生的，写上——例如「该转换在主代码里被手写 81 次，没有任何 helper」。
它把 ADR 从个人意见变成结构性证据。

代码里有做对了的地方，点名它作为「改这类代码前先读它」的正例锚点。>

## 考虑过的选项

<选项必须针对**这一整类问题**，不是针对那一次修复。
每个选项写：它是什么、它的吸引力在哪、为什么没选它，并**标明否决性质**：

  设计否决 —— 与系统的基本能力或约束冲突；永不回头，除非那个能力本身被取消。
  成本否决 —— 方案更优，但当下改造代价不可接受；代价变化时回头，必须进「何时重新评估」。
  待评估   —— 本条 ADR 没有裁决它，只是记录它存在；主动进「何时重新评估」。

不得把成本否决写成设计否决，也不得把待评估写成已否决。
「没认真考虑过」的选项不要列——列了反而掩盖真实的决策空间。>

## 裁决

<选了什么，以及**它固化成哪几条可复用规则**。

规则是这一节的实际产出：要具名、要能直接贴进 code review。
读者身份不同时分组，例如「开发规则」（写代码时守什么）与「调试规则」（排查时先看什么）。>

## 接受的妥协（诚实记录）

> 必填，不得为空或敷衍。记录**真实**理由——
> 「因改动成本而选它，不是因为它更好」必须如此写出。

## 何时重新评估

> 必填，不得为空或敷衍。写清什么条件成立时这个裁决就该被推翻。
> 每一条成本否决与待评估的选项都应在这里有对应触发条件。

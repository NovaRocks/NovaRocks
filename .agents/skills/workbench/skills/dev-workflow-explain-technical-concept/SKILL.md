# 技术概念讲解

目标是把用户不懂的概念讲清楚、讲透彻：用户能够用自己的话说明它解决什么问题、为什么这样运作，并推断条件变化后会怎样。
真实例子、逐步拆解、源码、对象表、资源账和配图都是帮助理解的手段，不是每次必须填满的输出模板。
保留因果链，按主题和用户要求选择深度；不要把某一次系统架构讲解的形式套到所有概念上。

## 先确定理解缺口与证据范围

1. 从当前问题和上下文判断用户卡在哪里：术语含义、机制为什么成立、具体怎么运行、两种方案有什么区别，还是某个现象
   为什么发生。只补齐理解它必需的前置概念，不重复用户已明确理解的内容；信息足够时直接讲，不先发问卷。
2. 保持只读：可以检查代码、文档、测试和日志，但不修改项目、不创建 goal，也不进入交付阶段。用户随后明确要求修改或
   发布时，再交回相应 skill。涉及项目工作流时完整读取 `../workbench/references/workflow-contract.md` 和适用的
   `AGENTS.md`；纯通用概念不为形式扫描无关仓库或要求 spec/plan。
3. 按主题取证：
   - 通用概念、算法或数学原理：讲清定义、成立条件和推导，不虚构项目背景或实现对象。
   - 当前系统或代码：核对真实调用链、数据结构、配置和测试。相关本地源码可用时优先查看，记录影响结论的版本；
     缺失或需要核实最新外部事实时再补充权威来源。
   - spec、plan、PR 或架构变化：分别核对原实现、目标设计和当前落地程度；计划、其他分支的执行记录不等于当前实现。
   - 故障或异常：区分已证实根因、证据支持的怀疑与尚未确认的部分。
4. 回看已有说法。若此前解释不严谨，先明确修正；未知的类型名、默认值、调用顺序或测试结果不要用合理猜测补齐。
   引用证据放在它所支撑的解释旁边，说明职责或推理作用；当前代码给出可核查的文件与行号，不把路径清单当讲解。

## 用一个具体例子建立共同背景

尽早选一个足以暴露关键机制、又能手工跟踪的例子，沿全文保持同一输入、标识和角色：

- 项目问题优先使用真实请求、测试数据、日志或可核查用例；通用概念可用明确假设的最小算例，不必强行寻找生产事故。
- 给出与问题有关的初始条件和具体值，例如一组待排序数字、一个条件概率问题、一次请求或一批数据。数量、规模和拓扑
  只引入推导需要的部分；不要用虚构的精确数值制造真实感。
- 区分实测轨迹、源码约束下的推演、目标设计示意和教学简化。真实数据上的改写请求不等于已执行的测试；示意类型或
  伪代码需标明，不能暗示某个 API 已存在。
- 解释变化前后时复用同一输入；增加边界情况时改变原例中的一个条件，说明它与主线的关系，不另起互不相关的故事。
- 类比可以建立直觉，但要回到概念本身，指出类比不成立的边界。

用户只追问一个局部问题时，继续使用已有例子并聚焦该处，不重新铺开整篇背景。确实只需一个定义或短算例即可回答时，
不强行扩成长篇流程。

## 沿因果链逐步展开

先说明问题背景、必要概念和理解路线，再让结论从例子中推导出来。不要用“一句话结论”或源码名词堆替代解释。
首次引入陌生术语时用中文说明它的含义和作用，必要时附英文全称；用户提到了某个缩写不代表已经理解它。

对每个关键步骤，讲清：**什么条件触发 → 谁或哪条规则起作用 → 输入怎样变化 → 得到什么结果 → 下一步为什么能继续。**
同时解释为什么需要这一步，以及省略它会有什么后果。用连贯文字呈现，不必逐步机械填写五个字段。

按主题选择需要展开的细节：

| 理解对象 | 沿例子追踪什么 | 何时可以停下 |
|---|---|---|
| 概念、算法、数学原理 | 定义与假设、具体值的逐步变化、关键不变量、推导为何成立 | 用户能从同一规则推断一个变式；无需附加类对象或资源配额 |
| 系统、代码或运行机制 | 参与者、实际类型与关键调用、数据与控制状态、同步与异步交接 | 关键行为已有具体承载者和触发条件；不追无关底层实现 |
| 设计变化、方案比较或异常 | 同一输入下的前后差异、必要条件、失败分支、收益与代价 | 能区分原理限制、主动取舍和实现问题；不自动扩成全量架构评审 |

不要用“交给调度器”“自动释放”“进入下一阶段”等话跳过用户正在追问的机制。需要更低一层时，展示少量关键伪代码、
公式或调用关系，再把它接回原例。

### 对象、生命周期与资源：仅在解释需要时展开

当问题涉及资源、并发、生命周期，或用户明确要求具体对象和申请/归还时，沿同一个请求追踪以下责任：

- 哪些服务在请求前已存在，哪些对象由本次工作构造；具体类型、数量、创建触发点和持有者是什么。
- 哪些是不可变定义，哪些是共享运行状态，哪些是实例私有状态；构造对象与激活它是否为同一时点。
- 控制权或所有权交给谁，传递的是值、引用还是跨进程副本；何种事实允许后继工作开始。
- 对象何时停止工作、释放引用、被销毁；业务完成、停止请求、实际退出、额度归还与底层分配最后释放是否分离。
- 有哪些真实额度或有界责任，各自的单位、作用域、申请时点、持有者、归还条件，以及申请失败或取消后的去向。

对象表可用“对象 / 构造时点 / 持有者 / 结束条件”，额度表可用“资源与单位 / 申请 / 持有 / 归还 / 不足时行为”。
没有配额就不造配额；配置上限、指标计数、逻辑窗口、物理内存和超时不是同一件事。额度归还不一定表示内存已释放，
局部完成也不一定证明远端已退出。只列影响本问题的资源，并说明覆盖范围，不能冒充系统全部资源账本。

## 用图和表减少理解负担

用户明确要求配图时提供与解释对应的图；未要求时，在关系、顺序或变化难以靠文字看清的地方主动配图。简单事实不强行画图。
按难点选表现方式，不固定图数或图种：

- 结构、拓扑或所有权图：谁与谁有关，边界在哪里。
- 时序、流程或状态图：谁先做什么、等待什么、何处并发或分支。
- 数值变化图、几何示意或小算例表：值怎样变化，为什么得到这个结果。
- 生命周期图或时间表：不同完成与释放时点怎样分离。

小型静态软件关系图优先用 Mermaid；参数变化或交互确实有助于理解时使用合适的可视化方式。图中的角色、标识、方向和
正文保持一致，随后解释关键箭头；不要把可能并发的事件画成必然全序，也不要把目标态画成已实现。复杂图按问题拆开，
不要把整篇术语塞进一张图。

并列比较或资源申请/归还有明确维度时使用表格；因果推导仍用正文。避免同一内容在正文、图和表中完整重复三遍。

## 补上边界、取舍和可迁移的理解

主线走通后，挑最能检验理解的一个条件变化、反例或失败分支，让用户看到前面的规则怎样继续适用。
比如改变输入分布、一个假设、消息到达顺序或可用容量；选择与主题有关的变化，不为所有概念附加取消、超时和重试。

在影响结论的地方区分：定义或基本约束决定了什么，设计主动选择了什么，当前实现做到了什么，最终有什么可观察影响。
这些是辨析维度，不是每个答案都必须有的四个章节。

讨论工程取舍时说明收益、代价和适用条件；不能把“目前这样实现”当成理论必然，也不能只讲没有现实约束的理想模型。
用户在问是否为 bug、能否避免或是否已经实现时，给出有证据的明确判断；证据不足则限定结论。

## 表达与收束

使用中文连贯解释，保留必要的标准术语和代码标识。每引入一个名字，先让读者知道它在例子里做什么。
长流程按有意义的里程碑编号、每步用短段落讲清变化；短问题直接聚焦。篇幅由理解缺口决定，不以步骤数、术语数或篇幅
证明“透彻”。

交付前检查：读者能否沿例子复述关键因果，能否区分事实与示意，能否预测改变一个条件后的结果？若只能记住名词、
“由框架处理”或结论口号，补齐缺失的推理；若某段不帮助回答这些问题，删去或压缩。

完整讲解后用一小段连接机制与结果，不重复目录，也不让追问代替本轮解释。需要继续交流时问“哪一段还没绕明白”，
并按仍值得展开的概念给少量入口；用户要求简短回答或只问局部问题时，不强制附加追问清单。

## 问题

独立参照引擎如何统一版本来源、按实际需求准备输入，并让所有测试消费本次运行冻结的准确引用？

## 背景与执行事实

参照输入遵循 ADR-0155 的推荐声明与缺失创建规则。Trino 镜像提供服务端与官方 CLI；JDBC 驱动是独立下载件。镜像存在不表示驱动也存在，场景需要哪些构件由原生声明决定。参照服务属于消费者持有的临时资源，不属于 ADR-0191 的常驻机器服务。

| 所有者 | 负责的事实 |
|---|---|
| `versions.json` | 唯一版本、平台变体、镜像别名、下载件内容与关联 |
| 输入 builder | 创建缺失构件；创建镜像别名前核对版本，保管核对容器直到真实退出 |
| 共用解析入口 | 按构件消费 builder 结果文件，返回准确 image ID 与下载件引用 |
| SQL/System runner | 根据最终选择汇总需求，解析一次并写入正常运行结果 |
| 用例 | 消费交入的准确引用，保管实际启动的服务或客户端直到退出 |

## 考虑过的选项

**各用例自行固定版本、查找镜像并核对。设计否决。** 用例会成为多个版本与缺失处理 owner，参照升级无法由一处声明决定。

**每次运行重新验证版本。设计否决。** 已创建别名按 ADR-0155 直接复用，运行入口不建立环境版本准入。维护者可显式诊断实际环境。

**统一声明、创建时核对、运行入口冻结引用。采用。** 版本选择归声明，供给归 builder，运行选择归 runner，用例只消费引用。

**解析命令日志取得机器结果。设计否决。** 冷创建会输出拉取或构建日志；结果文件与双流诊断应分别保留。

## 裁决

1. **单一声明规则。** 参照版本只在 `versions.json` 声明；驱动与手工 Maven 工具从同一声明取得版本。声明读取校验构件间的一致性。
2. **创建检查规则。** 仅在创建镜像别名前核对声明版本。核对命令属于 builder 的容器工作，必须持有准确身份，在成功、失败、超时与取消后观察实际退出及移除；回收失败与原失败共同报告。别名只在核对和回收成功后建立。
3. **结果分离规则。** builder 的机器可读结果通过原子结果文件交接；诊断与原始退出另行保留。消费者不从日志中猜结果。
4. **需求与引用规则。** 原生 suite/场景声明具体构件；入口对最终执行选择求并集，每种构件解析一次。列举与 dry-run 不准备输入。用例不得重新选择版本或回退到候选镜像。
5. **运行来源规则。** 正常与失败的运行结果均记录实际使用的 image ID、声明版本及所用驱动身份。记录事实不意味着重新验证版本，也不证明资源退出。
6. **历史与升级规则。** 代码注释、测试名、错误与用例标记不携带参照版本；以规则或源码符号说明依据。冻结语料与来源记录中的历史版本保留，语义基准升级须另行复核原有预期。

## 接受的妥协（诚实记录）

已有本地别名直接复用，因此手工错误重打别名不会在普通测试前被发现。该风险与 ADR-0155 一致；运行记录仍保留实际 image ID。使用可读 tag 不承诺不同机器取得字节相同的镜像。

首次需要缺失构件时可能联网。供给失败会使运行入口失败，而不是变成用例通过或 BLOCKED。参照场景属于显式重项，默认集合不要求参照引擎；其健康由相关修改、升级与手工轮次维护。

## 何时重新评估

- 若必须证明不同机器参照镜像字节相同，需要重新裁决供给身份与固定输入政策，不能在用例中恢复 digest 检查。
- 若增加客户端或参照系统，扩充构件声明和原 builder；只有出现不同生命周期或真正独立的供给 owner 时再调整边界。
- 若参照变为常驻服务，需要重新裁决机器服务所有权和运行引用，不能隐式加入普通 fixture 启动。
